# /curate — Wiki 知识治理

## 触发

`/curate` 处理 wiki 中**已经存在但需要修改、退役或删除**的内容。
与 `/ingest`（新增）、`/think`（沉淀对话）、`/query`（检索）形成互补。

典型触发场景：

- 用户说"这条数据错了"/"这个判断要改"/"这页过时了"
- `/lint` 报告中的 P0 #3（conflict 超期）、P0 #5（过时数据）需要进入修复流程
- 用户主动说"帮我清理一下 deprecated 页面"
- 跨页同步：某个事实变更需要在多个页面一致更新
- 用户在对话中明确否证了某个已沉淀的论点

## 工作模式

| 模式 | 触发条件 | 行为 |
|------|---------|------|
| **修正模式** | 数据/事实错误，但页面整体仍有效 | 软删除原内容 + 标注更正 + 新来源 + version 更新 |
| **退役模式** | 页面整体过时或被新版替代 | `status: deprecated` + `superseded_by` 链 + 索引迁移 |
| **解冲突模式** | `status: conflict` 需要收尾 | 引导用户判断 → 选定主版本 → 另一支降级或退役 |
| **删除模式** | 内容被证伪、重复或彻底无价值 | 软删除（默认）/ 硬删除（显式授权） |
| **批量同步模式** | 一个事实影响多页 | 列出受影响页面 → 逐页应用修正 |
| **lint 消费模式** | 用户提供 lint 报告 / 刚跑完 lint | 解析报告 → 分类 → 逐项处理 |

## 核心原则

1. **保留可追溯性**：默认软删除，原内容用删除线 + `[{date} 更正]` 标注，留 git 兜底
2. **来源优先**：任何修正必须给出新来源（如无新来源，标 `status: draft` 或 `conflict`）
3. **变更必登记**：所有 curate 操作都进 `knowledge/wiki/log.md`，类型为 `curate`
4. **不替用户决断**：冲突解决、deprecated 与否、是否硬删除，最终由用户拍板
5. **维持双向一致**：`supersedes`/`superseded_by`、`see_also`、index 三者必须同步

## 工作流程

### 阶段 1：定位目标

接到 curate 请求后，先**完整理解要改什么**：

- 用户给的是页面 id？→ 直接 Read 该页
- 用户描述的是某条事实？→ 走 `/query` 的 L1+L2 定位（轻量版，跳过 L3）
- 用户给的是 lint 报告条目？→ 按报告中的文件路径直接 Read
- 跨页影响？→ 用 `bash .coco/skills/query/scripts/search.sh fulltext {keyword}` 找出所有相关页面

定位后必须读取**完整 frontmatter**，确认：
- 当前 `status`、`version`、`supersedes`/`superseded_by` 链
- 该页被哪些页面 `see_also` 引用（决定改名/退役时的连锁影响）
- 是否在 `knowledge/wiki/index.md` 收录

### 阶段 2：与用户确认操作方案

在执行写入前**必须**用一句话向用户确认动作：

```
我打算对 [[page-id]] 做 {修正/退役/解冲突/软删除}：
- 具体变更：{一句话描述}
- 影响范围：{是否涉及其他页面、index、log}
- 新来源：{来源 id 或 "无新来源，将标 draft"}
确认执行？
```

仅在以下情形可省略二次确认：
- 用户已经给了非常具体的指令（如"把第 X 条改成 Y，来源是 Z"）
- 在 lint 消费模式下，用户已批量授权一组修复

### 阶段 3：执行写入

按模式选择子流程，详见 `reference/curate-rules.md`：

| 模式 | 子流程 | 详细规范位置 |
|------|--------|-------------|
| 修正 | 软删除 + 更正标注 | `reference/curate-rules.md` §1 |
| 退役 | deprecated + supersedes 链 | `reference/curate-rules.md` §2 |
| 解冲突 | 选主 + 降级旁支 | `reference/curate-rules.md` §3 |
| 删除 | 软删除 / 硬删除 | `reference/curate-rules.md` §4 |
| 批量同步 | 跨页一致性 | `reference/curate-rules.md` §5 |

每个子流程都遵守同一个写入合同：
- `version` 更新为今天
- 必须有 `[YYYY-MM-DD 更正/退役/...]` 标注
- 至少 1 条 `[[wikilink]]` 指向新来源或继任页面

### 阶段 4：连锁更新

任何实质性变更后必须检查并同步：

| 检查项 | 操作 |
|------|------|
| `knowledge/wiki/index.md` 中的条目 | 更新 summary（如变化）/ 加 `[deprecated]` 标签 / 改 status |
| 反向 `see_also` 引用 | 被改名/退役的页面，所有引用方都要同步 |
| `supersedes` ↔ `superseded_by` 对称性 | 若改 supersedes 链，对应另一端必须同步 |
| `knowledge/wiki/log.md` | 追加 `## [YYYY-MM-DD] curate \| {操作摘要}` |
| `knowledge/schema/glossary.md` | 若术语改名/废弃，同步 glossary 条目 |

### 阶段 5：自检与摘要

写入完成后跑一次轻量自检（不必跑完整 lint）：

- 改过的页面是否仍满足最小 frontmatter 要求？
- supersedes 链是否对称？
- 是否所有反向引用都已同步？

输出摘要给用户：

```markdown
## 治理完成

**模式**：{修正 / 退役 / 解冲突 / 删除 / 批量同步}

**主操作页面**：
- [[page-id]] — {一句话说明做了什么} (version: YYYY-MM-DD)

**连锁更新页面**：
- [[other-page-1]] — {一句话说明}
- [[other-page-2]] — ...

**索引/日志**：
- index.md：{已更新 / 无需更新}
- log.md：已追加 curate 条目

**待跟进**：
- {建议下次 lint 关注的项 / 建议补充的素材}
- 无
```

## 与其他 Skill 的协作

| 场景 | 协作方式 |
|------|---------|
| `/lint` 报告 P0/P1 项 | curate 直接消费报告作为输入清单 |
| 修正后需要补充新素材 | 收尾时建议 `/ingest` 新来源 |
| 退役页面有继任者 | 继任者可能由 `/ingest` 或 `/think` 新建 |
| 治理触发了大量变更 | 收尾建议跑 `/lint` 验证健康度 |
| 用户在 `/think` 沉淀时矛盾旧论点 | 由 think 标记 → curate 接管修正/退役 |

## 与 /ingest 的边界

| 维度 | /ingest | /curate |
|------|---------|---------|
| 默认操作 | 增量追加 | 修改 / 标注 / 退役 |
| 是否允许删除 | ❌ 禁止 | ✅ 软删除（默认）/ 硬删除（授权） |
| 是否允许覆盖 | ❌ 禁止 | ✅ 修正模式下允许（必须留痕） |
| 触发时机 | 新素材入库 | 已有内容失效或错误 |
| version 更新 | 追加新内容时更新 | 任何治理操作都更新 |

**误用纠正**：
- 用户说"补一条新数据" → 是 `/ingest`，不是 `/curate`
- 用户说"补的那条数据其实是错的" → 是 `/curate`
- 用户说"这页其实有更新版本了" → 是 `/curate`（退役旧版） + `/ingest`（建新版）

## 软删除 vs 硬删除

**默认走软删除**。理由：知识库的核心价值不在"最新对"，而在"能溯源 + 能看到判断演进"。

| 类型 | 操作 | 适用场景 |
|------|------|---------|
| **软删除（默认）** | 原文加 `~~删除线~~` + `[YYYY-MM-DD 删除：{原因}]` 标注；frontmatter 不动 | 错误数据、过时事实、未删干净的旧观点 |
| **页面级退役** | `status: deprecated`，正文保留，加顶部 deprecation 提示 | 整页失效但有历史价值 |
| **硬删除** | 直接删除文件 / 段落，仅 git 留痕 | 用户**显式授权**且内容明确无价值（机器人误生成、重复页、空页） |

硬删除前必须满足：
1. 用户明确说"删掉文件"/"硬删"/"彻底删除"
2. 该页未被其他页面 `see_also` 或 `supersedes` 引用（否则先解依赖）
3. 已在 log.md 记录原因

## 约束

- **不捏造来源**：修正必须有新来源；如无，记 `draft` 或 `conflict`，不强行下结论
- **不擅自定胜负**：解冲突时呈现两方，最终由用户选；选定后另一方仍保留为 deprecated（带原文）
- **不改别人的引用片段**：原始引用即使被证伪也保留原文 + 加证伪标注
- **不静默退役**：deprecated 必须配 superseded_by（除非整个主题被废弃，此时记录原因）
- **不绕过 log**：所有 curate 操作必须进 log.md，否则后续无法审计

## 边界情况

| 场景 | 处理方式 |
|------|---------|
| 用户要修但说不清改成什么 | 先标 `status: conflict` + 在正文加 `[需要补充新来源]` 注，不强行改 |
| 修正会牵连 5+ 页面 | 进入批量同步模式，先列受影响清单让用户预览，再分批执行 |
| 退役但找不到继任者 | `superseded_by: []` + 在 log 注明"暂无继任者"；不强造一个新页 |
| 解冲突时两方都有部分对 | 新建合并版页面 → 两个旧版都标 deprecated 指向新版 |
| 用户要硬删但有反向引用 | 先列出所有反向引用 → 询问是先解依赖还是改为软删除 |
| 跨语言/跨译名的同义重复页 | 选其中一页为主，另一页 deprecated 指向主页；同步 glossary |
| 已经 deprecated 的页面又被引用 | 提示用户：考虑解除 deprecated（若内容仍有效）或建议引用方改指向继任者 |
